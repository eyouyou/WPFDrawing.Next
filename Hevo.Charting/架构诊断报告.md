## 一、执行摘要

| 维度 | 评级 | 主要结论 |
|------|------|---------|
| 整体架构 | ★★★★☆ | ECS + 数据驱动管线设计思路先进，核心 RWLock 并发模型正确 |
| 线程安全 | ★★★☆☆ | 存在 3 处真实数据竞争，1 处事件订阅竞争，整体可控但有盲区 |
| 内存安全 | ★★★☆☆ | ArrayPool 租借数组与渲染读取之间存在生命周期重叠风险 |
| 性能 | ★★★☆☆ | UsePort 脏检查机制因实现细节完全失效，热路径每帧 2~4 次 GC 分配 |
| API 易用性 | ★★★☆☆ | 语法糖覆盖不均，K 线场景心智负担远高于分时图 |

**最高优先修复项**：键盘写锁缺失（DEBUG 崩溃）、UsePort 脏检查失效（性能核心）、ArrayPool 读写竞争（数据正确性）。

## 二、架构与模式审查

### 2.1 整体架构优势

| 设计 | 说明 |
|------|------|
| **三明治渲染模型** | SkiaSharp（光栅）/ DrawingVisual（矢量）/ InteractionCanvas（控件）物理隔离，动静分离，边界清晰 |
| **ECS 特质系统** | ChartFeature（System）、Trait（Component）、ChartLayer（Entity）三者职责分明，无循环依赖 |
| **宏观 RWLock 并发** | `ReaderWriterLockSlim` 保证一帧内所有 Feature 读取的数据处于同一快照，防止时空撕裂 |
| **VersionToken 无限纪元** | 封杀大小比较，long 溢出后环形运转，理论上可永久运行 |
| **按需 VSync** | `CompositionTarget.Rendering` 按需挂载/摘除，静置时 GPU 不空转 |
| **ViewportPorts 全家桶** | 五引脚打包传递，消灭引脚散落问题 |
| **FieldMeta SSOT** | 名称/格式/颜色一处定义，多处联动 |

### 2.2 架构违规点

#### ❌ V1：`CombinedAspect` 实现与文档不符

**文档**（`00.Hevo.Charting 架构协议与开发规范.md §7.2`）声称 `operator +` 生成扁平列表，`Compose` 遍历复杂度为 O(N)。

**实际代码**（`Aspect.cs:47`）：
```csharp
public static ChartAspect operator +(ChartAspect left, ChartAspect right)
{
    return new CombinedAspect(left, right); // ← 构建二叉树，非扁平列表
}
```

10 个 Feature 经 `Aspect += feature` 后产生深度为 9 的嵌套 `CombinedAspect`。`Decompose` 递归遍历此树。**文档与实现必须二选一对齐**。

> 注：数据流组合通过 `_orderedFeatures` 数组完成（真正的 O(N) 平坦遍历），二叉树仅影响 `Decorate()` 调用路径，实际运行时危害较小，但认知误导严重。

---

#### ❌ V2：`ChartInteractionFeature.Phase` 越界枚举

```csharp
public override FeaturePhase Phase => (FeaturePhase)(-5); // ← 超出枚举定义范围的魔术数字
```

`FeaturePhase` 枚举最小值为 `Layout = 0`。使用 `-5` 意图让交互 Feature 在所有 Feature 之前执行，但这是一个未被文档化的"私约"，后续开发者无从知晓。应将 `PreLayout = -5` 显式加入枚举定义。

---

#### ❌ V3：`ReactiveSchema.ComposeAll` 违反单一职责

该方法超过 100 行，同时承担：
1. Feature 排序与 Aspect 树构建
2. 调用基类 `ComposeAll`
3. 构建 Rx 数据流管线
4. 注册 `OnPortUpdated` 事件
5. DEBUG 模式调试菜单注入

建议拆分为：`BuildFeatureGraph()`、`BuildDataPipeline()`、`InjectDebugTools()`。

---

#### ❌ V4：`KLineSchema` 状态泄漏到 Schema 层

```csharp
// KLineSchema.cs — 这两个字段属于 DataSource 的职责，不属于 Schema
private DateTime _lastFallbackTime = DateTime.MinValue;
private bool _isHeartbeatRunning = false;
```

Schema 的职责是"声明式装配管道"，不应承载运行时保活逻辑。根因是 `ReactiveDataSource` 基类没有提供标准化的"心跳/断层恢复"扩展点，迫使用户在 Schema 层打补丁。

---

#### ❌ V5：`DisposeWith` 在两个文件中重复定义

`ChartFeature.cs:200`（`RenderFlowLifecycleExtensions`）和 `WorkflowWPFEventExtension.cs:9`（`WorkflowWPFEventExtension`）中存在**两个方法签名完全相同**的扩展方法：

```csharp
// 两处均为：
public static IRenderFlow<T> DisposeWith<T>(this IRenderFlow<T> source, ChartFeature feature)
```

同时 `using` 两个命名空间时会触发 **CS0121 编译器歧义错误**。

## 三、线程安全分析

### 并发模型总览

```
后台线程池 (WatchAsync / HevoDispatcher.FireAndForget)
    │
    ├─► DataBlackboard.BeginTransaction() [WriteLock 排他]
    │       └─► 写入 DataPort → EndTransaction → NotifyPort → OnPortUpdated
    │
    └─► chart.RequestUpdate() → Dispatcher.InvokeAsync (投递到 UI 线程)
                                         │
                                         ▼
UI 线程 (WPF Dispatcher)
    ├─► OnCompositionTargetRendering
    │       ├─► ReactiveSchema.ProjectAll() [ReadLock 快照]
    │       ├─► RenderContext.SubmitSync()  [无锁，仅 UI 线程]
    │       └─► layer.Update(snapshot)     [无锁，仅 UI 线程]
    │
    └─► WPF 事件 (MouseMove / KeyDown)
            └─► WithBoard(flow) → AcquireUpgradeableReadLock
```

### 3.1 T1：`HandleKeyboardNavigation` 缺少写锁（严重，DEBUG 崩溃）

**位置**：`ChartInteractionFeature.cs:348`

```csharp
private void HandleKeyboardNavigation(ChartCell chart, RenderContext ctx, DataBlackboard board, int indexDelta)
{
    ...
    // ❌ 直接裸写！WithBoard 提供的是 UpgradeableReadLock，而非 WriteLock
    board.WriteIfChanged(Viewport.UserRange, new DoubleRange(newMin, newMax));
    ...
}
```

`WriteIfChanged` → `ForceWrite` 的 DEBUG 检查：
```csharp
if (!_rwLock.IsWriteLockHeld)
    throw new InvalidOperationException("[黑板越权篡改]");
```

**影响**：DEBUG 构建下，用户一按方向键即崩溃；Release 构建下，`UserRange` 在无写锁保护下被并发修改，可能与 `ViewportManagerFeature` 的 `WatchAsync` 读取发生数据竞争。

**正确写法**（参考同文件 `HandlePan:217`）：
```csharp
using (board.AcquireWriteLock())
{
    board.WriteIfChanged(Viewport.UserRange, new DoubleRange(newMin, newMax));
}
```

---

### 3.2 T2：`WorkflowTrigger` 委托操作非线程安全（中危）

**位置**：`WorkflowTrigger.cs:13-27`

```csharp
public class WorkflowTrigger<T> : IWorkflow<T>
{
    private Action<T>? _subscribers; // ← 无 volatile，无锁

    public IDisposable Subscribe(Action<T> onNext, ...)
    {
        _subscribers += onNext;  // ← 非原子的读-改-写
        ...
    }

    public void Push(T data)
    {
        _subscribers?.Invoke(data); // ← 并发读
    }
}
```

`Subscribe` 由 UI 线程在初始化时调用，`Push` 由 `ReactiveDataSource` 在后台线程（`lock(_lock)` 内）调用。若初始化阶段尚未完成（如异步加载时有新订阅者），而后台同时 Push，`_subscribers` 的读改写存在竞争。

**修复方向**：使用 `Interlocked.CompareExchange` 实现无锁委托更新，或加 `lock`。

---

### 3.3 T3：`OnTransactionCommitted` 事件摘除不在锁内（中危）

**位置**：`FeatureComputeExtensions.cs:131-141`（`DoOnDispose` 回调）

```csharp
return hookedFlow.DoOnDispose(() =>
{
    if (currentBoard != null)
    {
        ...
        currentBoard.OnTransactionCommitted -= commitHandler; // ← 无锁！
        currentBoard = null;
    }
});
```

`DoOnDispose` 在 `DecomposeAll`（UI 线程）时触发。与此同时，后台线程可能正在 `EndTransaction` 中执行：

```csharp
// DataBlackboard.EndTransaction（持有 WriteLock）
foreach (var port in portsToNotify) NotifyPort(port);
OnTransactionCommitted?.Invoke(this); // ← 读取并调用事件
```

在 .NET 中，`event -=` 操作（委托 `Delegate.Remove`）与事件调用（`?.Invoke`）并发执行时，由于委托是不可变引用类型，读到的是旧引用还是新引用取决于内存模型，理论上安全，但 `commitHandler` 捕获了 `isDirty` 等局部变量引用，Dispose 后继续被调用可能导致逻辑错误（向已销毁的 Feature 发送通知）。

**修复方向**：`DataBlackboard` 应提供受锁保护的 `RemoveTransactionListener` 方法；或在 `commitHandler` 内检查存活标志。

---

### 3.4 T4：`Blackboard_OnPortUpdated` 中 `_attachedChart` 的 TOCTOU 竞争（低危）

**位置**：`ReactiveSchema.cs:316-326`

```csharp
private void Blackboard_OnPortUpdated(object port) // 后台线程调用
{
    if (_attachedChart == null) return;         // 检查点 1（后台线程）
    if (Registry.NotifyPortUpdated(port))
    {
        _attachedChart.RequestUpdate(_ => { }); // 使用点 2（后台线程）
    }
}
```

UI 线程的 `DecomposeAll` 可在检查点 1 之后、使用点 2 之前将 `_attachedChart` 设为 `null`。

**实际风险**：低。最坏情况是对已卸载的 `ChartCell` 调用 `RequestUpdate`，该方法本身有 `Dispatcher.InvokeAsync` 保护，WPF 控件卸载后调度会静默失败。但应补充 null 二次校验消除 TOCTOU 读取。

---

### 3.5 T5：`ChartInteractionFeature._isFetching` 非 volatile（低危）

**位置**：`ChartInteractionFeature.cs:399`

```csharp
private bool _isFetching = false; // ← 无 volatile 修饰
```

`_isFetching = true` 由 UI 线程在 `CheckBoundaries` 中设置，`_isFetching = false` 由 `FireRequestAsync` 的 `finally` 块（线程池 continuation）设置。没有 `volatile` 时，编译器或 CPU 可能将读取缓存，导致 UI 线程看不到后台已将其置 `false`，从而错误地持续跳过数据请求。

**修复方向**：改为 `private volatile bool _isFetching` 或使用 `Interlocked.Exchange`。

## 四、内存安全分析

### 4.1 M1：ArrayPool 租借数组与渲染读取之间的生命周期重叠（严重）

**位置**：`DataPipeExtensions.cs:103-136`（`ColumnMapper.MapAndWrite`）

**问题**：`ColumnMapper` 使用 `ArrayPool<TValue>.Shared` 租借数组，并将其包装为 `ReadOnlyMemory<TValue>` 写入黑板。当视口大小不变时，**原数组不归还，直接原地写入新数据**：

```csharp
// ColumnMapper.MapAndWrite
if (_rentedArray == null || _rentedArray.Length < visibleCount)
{
    if (_rentedArray != null) ArrayPool<TValue>.Shared.Return(_rentedArray); // 仅在扩容时归还
    _rentedArray = ArrayPool<TValue>.Shared.Rent(visibleCount);
}

// 直接向 _rentedArray 写入新帧数据（原地覆写）
Span<TValue> span = _rentedArray.AsSpan(0, visibleCount);
span.Fill(_defaultValue);
for (int i = 0; i < visibleCount; i++) span[i] = _valueSelector(source[startIdx + i]);

board.ForceWrite(_targetPort, new ReadOnlyMemory<TValue>(_rentedArray, 0, visibleCount));
```

**竞争时序**：

```
UI 线程                               后台线程
────────────────                      ─────────────────────────────
ProjectAll (ReadLock)
  └─ OnProject 读取 ReadOnlyMemory        
     包装 _rentedArray[0..500]
     发布到 Layer 草稿箱
ReadLock 释放
                                      新数据到达，BeginTransaction (WriteLock)
                                        MapAndWrite：向 _rentedArray[0..500]
                                        直接原地写入新值 ← 此时 UI 线程正在渲染！
SubmitSync (无锁)
  └─ OnUpdate 读取 Layer 草稿箱中
     的 ReadOnlyMemory (指向 _rentedArray)
     → 读到了被后台部分覆写的数据！
WriteLock 释放
```

`OnUpdate` 在 ReadLock 之外执行，WriteLock 不保护已发布的 `ReadOnlyMemory` 内容，两个线程在同一块内存上发生未同步的读写。

**实际影响**：在 60fps + 高频 Tick 场景下，可能出现 K 线数据错位（某几根 K 线的 Open/Close 混入了相邻时间点的值），表现为偶发的价格跳动错误，极难复现。

**修复方向**：在 `ProjectAll` 结束后、`SubmitSync` 之前，对已引用 `ReadOnlyMemory<T>` 的 Trait 数据进行浅拷贝（复制数组引用，而非内容），或改为双缓冲数组切换策略。

---

### 4.2 M2：`UseState`/`UseMemo` Hook 状态因 H1 Bug 每帧重置（严重）

**位置**：`FeatureContextExtensions.cs:16-37`，`ChartFeature.cs:141`

由于 `ChartFeature.Project()` 每帧创建新 `FeatureContext`，`_hookPocket` 和 `_dynamicStatePocket` 每帧清空。

```csharp
// CandleFeature.OnProject
var (_, areaChanged) = ctx.UseDynamicMemo("Area", currentArea, area => area);
// ↑ 每帧 _dynamicStatePocket 为空 → 每帧插入新 MemoState → areaChanged 永远为 true
```

**连锁影响**：`needRedrawStatic` 永远为 `true`，K 线静态层每帧全量重绘，而不是仅在视口/数据变化时重绘。这是**双重失效**——既有 UsePort 无法检查脏状态（H1），又有 UseMemo 无法记忆上一帧结果。

### 4.3 M3：`_lastSource` 强引用阻止旧快照 GC（低危）

**位置**：`DataPipeExtensions.cs:92`

```csharp
private IReadOnlyList<TItem>? _lastSource; // 防抖用，持有上一帧快照强引用
```

当 `DataSource` 因新数据产生新快照时，`ColumnMapper._lastSource` 仍持有旧快照的强引用，阻止 GC 回收。对于百万级 K 线数据，这意味着前一帧的完整快照数组无法及时释放，瞬时内存峰值加倍。

---

### 4.4 M4：`ReactiveDataSource` 中 `RequestAsync` 的 `CancellationTokenRegistration` 生命周期

**位置**：`DataSource.cs:186`

```csharp
await using var registration = token.CanBeCanceled
    ? token.Register(() => tcs.TrySetCanceled(token))
    : default;
```

使用了 `await using`（`IAsyncDisposable`），确保 registration 在方法退出时注销，防止 `tcs` 被取消的 Token 持有。这是**正确实现**，值得保留作为范式。

---

### 4.5 M5：`VisualDataBag.RentSnapshot` 的借出数组未归还风险（低危）

**位置**：`RenderContext.cs:248-268`（`PrepareTasks`）

```csharp
var globalSnap = _liveGlobalData.RentSnapshot();
var localSnap = liveLocal.RentSnapshot();
```

`RentSnapshot` 从 `ArrayPool` 借出数组。这些数组由 `FrameSnapshot` 持有，并在 `FrameSnapshot.Dispose()` 时归还。若 `FrameSnapshot` 未被正确 `Dispose`（如 `ExecutePipeline` 抛出异常），数组将永久泄漏。

**建议**：确认 `ExecutePipeline` 的所有退出路径均通过 `using var frame = ...` 覆盖。

## 五、性能与 GC 隐患

### 5.1 UsePort 脏检查机制完全失效（根因分析）

**位置**：`ChartFeature.cs:134-151`

**现象**：`UsePort<T>()` 在理论上应返回 `(value, changed=false)` 以阻止不必要的重绘，但实际上**每帧都返回 `changed=true`**。

**根因**：`Project()` 每帧构造全新的 `FeatureContext`：

```csharp
public void Project(RenderContext ctx, DataBlackboard board, SubscriptionRegistry registry, bool isFullPass)
{
    // ❌ 每帧 new！_portTokens 字典随之清空，上一帧的 VersionToken 记录全部丢失
    var localContext = new FeatureContext
    {
        _registry = registry,
        _currentFeature = this,
        _isFullPass = isFullPass
    };
    localContext.BeginProject(ctx, board);
    OnProject(localContext);
    localContext.EndProject();
}
```

`UsePort` 内部的脏检查：
```csharp
if (!_portTokens.TryGetValue(port, out var lastToken) || lastToken != currentToken)
// ↑ _portTokens 为新空字典，TryGetValue 永远 false → changed 永远 true
```

**副作用链**：

```
每帧 new FeatureContext
  ↓
_portTokens 清空 → UsePort 永远返回 changed=true
  ↓
_dynamicStatePocket 清空 → UseDynamicMemo 永远返回 changed=true
  ↓
所有 Feature 的 OnProject 每帧执行全量逻辑
  ↓
所有图层每帧标脏 → 每帧全量重绘
  ↓
SkiaSharp 每帧执行完整绘制指令序列（丧失动静分离优化）
```

同时，`private readonly FeatureContext _context = new();`（`ChartFeature.cs:123`）字段被声明但**从未使用**，是遗留死代码，说明此处曾有正确的复用设计，后被错误地改为每帧 new。

---

### 5.2 热路径 GC 分配清单

以下分配在每帧渲染周期内**必然发生**，与数据是否变化无关：

| 位置 | 代码 | 每帧分配 |
|------|------|---------|
| `ChartFeature.cs:141` | `new FeatureContext { }` | N × FeatureContext（N = Feature 数量）|
| `SubscriptionRegistry.cs:244` | `return new List<ChartFeature>()` | 1 × 空 List（空闲帧）|
| `ReactiveSchema.cs:109` | `new HashSet<ChartFeature>(dirtyList)` | 1 × HashSet（有脏帧）|
| `ChartCell.cs:165` | `.OfType<ChartLayer>().Where(...).ToList()` | LINQ 迭代器 + List |
| `ChartCell.cs:471` | `_visualRegistry.Select(x => x.Layer)` | LINQ 迭代器（AddLayer 时）|

---

### 5.3 `SoAColumnSlicer` O(N) 全量比较

**位置**：`DataPipeExtensions.cs:262`

```csharp
if (oldSlice.Length == safeCount && oldSlice.Span.SequenceEqual(sourceSpan)) return;
```

对大型切片数组全量 `SequenceEqual`，在百万级数据、高频 Tick 场景下，此代码处于每帧数据管线热路径，CPU 开销不容忽视。建议改为基于数据版本号或引用相等的快速判断。

### 6.2 `async void` 异常风险

**位置**：`ChartInteractionFeature.cs:461`


`async void` 方法在 `await` 后抛出的异常为 `UnobservedException`。虽然内部有 `catch`，但第三方网络库内部异常或 `OperationCanceledException` 的特殊子类仍可能绕过，导致进程崩溃。应改为 `async Task`，以 fire-and-forget 方式调用并处理返回的 Task。

### 6.3 用户接口心智负担分析

通过对比三个真实 Schema 的调用代码，量化用户编写一个新图表时的必要操作：

#### 6.3.1 DataPort 声明"三角形"耦合

用户必须在三处维护同一个端口：

```
① Schema 字段声明:   private readonly DataPort<ReadOnlyMemory<float>> ClosePort = new();
② 管道映射:          cfg.Slice(ClosePort, block => block.Closes);
③ Feature 注入:      new CandleFeature { ..., ClosePort = ClosePort, ... }
```

任何重命名或类型变更需同步修改三处，高度重复，易遗漏。

#### 6.3.2 ViewportPorts 全家桶仍需手动传递 6 次

```csharp
// K 线 Schema 中，VP 被手动传递 6 次：

.LinkSoAViewportStream(VP.ActiveRange, VP.Offset, ...)

```

ViewportPorts 的设计消灭了"引脚满天飞"，但没有消灭"全家桶满天飞"。

#### 6.3.3 CandleFeature 7 参数初始化（语法糖覆盖不均）


#### 6.3.4 `KLineSchema.OnRequireDataAsync` 胖 Lambda

```csharp

{
    ...
    OnRequireDataAsync = async (anchorIndex, count) =>
    {
```

#### 6.3.5 `GridLayoutFeature` 不透明的默认覆盖规则

框架在 `ReactiveSchema.ComposeAll` 中注入了默认 `GridLayoutFeature`，但用户在 `DefineFeatures` 中调用 `canvas.Use(new GridLayoutFeature { ... })` 时会再注入一个，最终哪个生效、优先级规则完全不透明。应提供 `protected virtual GridLayoutConfig DefaultLayout` 属性，让用户通过 override 而不是再次 Use 来自定义边距。

#### 6.3.6 `FieldMeta.Literal` 的 `HevoSolidBrush` 包装负担


#### 6.3.7 `static` vs `instance` DataPort 不一致
