## P0 — 必须修复

### 项 1. LineLayer.TrimPolylineToPlotArea 0-GC 修复

**现状**(`Layers/LineLayer.cs:156-170`)
```csharp
pts.RemoveRange(0, leftIn);     // O(N) 数组移位
pts.Insert(0, new HevoPoint);   // 头部插入,触发整段 memmove
```
每帧若曲线越界即触发,违反 §5"0 GC 稳态"。

**目标**:稳态零分配、零 memmove。

**改动方案**
1. 在 `LineLayer` 内提升两个字段:`private readonly List<HevoPoint> _trimmedBuffer = new(2048);`
2. 重写 `TrimPolylineToPlotArea`,改为**双指针扫描**输入 `screenPoints`,直接写入 `_trimmedBuffer`:
   - 先 `_trimmedBuffer.Clear()`(只重置 Count,不释放底层数组)
   - 单遍扫描,在交边界处插入交点,在区间内点直接 Add
   - 返回 `_trimmedBuffer`(或其 Span)
3. `OnUpdate` 末尾不要返回新 List,而把渲染指令直接基于 `_trimmedBuffer` 录制

**验收**
- BenchmarkDotNet 微基准:Trim 路径 Gen0/Gen1 均为 0
- 视觉回归:边界裁剪结果与原实现一致
- 单元测试:覆盖纯内、纯外、左穿、右穿、双穿四种情形

---

### 项 2. (撤销) 分发显式化 + Hardware/Widget 校验

**结论**:撤销此项,补充以下说明。

**实际查证**:
1. `RenderWidgetLayers()` 遍历 **ALL** active layers(含 Hardware),Widget 命令通过 `WidgetPool.Sync` 正确路由,**不存在静默丢弃**
2. `WpfRenderProvider.GetRenderer<WidgetBuffer>()` 与 `SkiaRenderProvider.GetRenderer<WidgetBuffer>()` 都返回 null,`LayerBuffer.Execute` 内的 widget 分支自动 no-op,**也不会双渲染**
3. `OnUpdate(IVisualData data, IDrawingSink draw, WidgetBuffer widget)` 已按 API 参数类型把 Drawing/Widget 分开,无需声明式 BufferKind

**剩余的"分发拆出独立 Dispatcher"价值有限**:`RenderWpfLayers` / `RenderWidgetLayers` / `OnSkiaPaintSurface` 已经命名清晰,且都依赖 ChartCell 的物理字段(`_drawingCanvas`, `_skiaElement`, `_interactionCanvas`),抽走会增加间接性而不增加表达力。

→ **此项无落地动作**。仅在 ChartCell 顶部补一条注释明确"三套 buffer 的渲染路径"即可。

---

### 项 3. VisualDependencyTracker 接入或移除

**现状**:`Abstractions/ChartLayer.cs:67-98` 定义了 `CheckIfDirty()`,但全代码库无调用。

**决策选项**
- **A. 接入**:把 `CheckIfDirty` 接到 `ChartLayer.CheckDirtyState()` 默认实现里,基于上一帧访问的 trait 引用相等性自动判脏,Layer 子类无需手写 dirty 逻辑
- **B. 移除**:确认现有 `IsDirty` + 显式 `MarkDirty()` 已够用,删除 `VisualDependencyTracker` 与 `TrackerDataProxy`

**建议**:走 **A**。理由:目前 Layer 子类大多没有 `CheckDirtyState` 重写,实际上是"每帧都重画",装备好自动 trait dirty 后能省掉一半重绘。

**A 方案改动**
1. `ChartLayer.OnUpdate` 包一层 `TrackerDataProxy`,自动记录本帧访问的 TraitId
2. `CheckDirtyState` 默认实现:`return _tracker.CheckIfDirty(currentLocalBag, currentGlobalBag);`
3. 首帧无记录 → 返回 true(强制画一次)

**验收**
- 静态场景下,Profiler 显示 Layer.OnUpdate 调用次数 ≈ 0
- 改 trait 后下一帧立刻重绘

## P1 — 工程整洁度

### 项 4. (撤销) IDrawingSink 与 DrawingBuffer 解耦

**结论**:撤销此项。

**实际查证**:
- 全代码库**仅** `DrawingBuffer` 一个类实现 `IDrawingSink`,无任何替代 Sink 实现
- 当前 `IDrawingSink` 已是纯接口(单方法 `Push(DrawCmd)`),角色清晰
- 即便未来要插入 BatchingSink/LoggingSink 等装饰器,任何外部类都可直接 `class XxxSink : IDrawingSink`,无需先把 DrawingBuffer 解绑
- 所谓"解耦"实际只是把直接实现改成适配器模式,引入间接性而无功能差别 (YAGNI)

→ **此项无落地动作**。当真有第二种 Sink 实现需求时再做。

---

### 项 5. 文本布局逻辑抽公共 helper

**现状**:`Renderers/DrawingRenderer.cs:100-143`(WPF)与 `Renderers/SkiaRenderer.cs:218-261`(Skia)中文本对齐、padding、background、baseline 计算重复 ~40 行。

**改动方案**
1. 新建 `Renderers/TextLayoutHelper.cs`,提供纯计算静态方法:
   ```csharp
   public static TextLayoutResult Compute(
       in HevoRect anchor, in HevoSize textSize,
       HevoTextAlignment align, in HevoThickness padding);
   ```
2. `TextLayoutResult` 包含 `BoundingRect`、`TextOrigin`、`BackgroundRect`
3. WPF/Skia Renderer 的文本分支只剩"调 Helper + 翻译为各自 API"

**验收**
- 两处文本分支代码总行数下降 ≥ 40%
- 像素级一致(快照对比)

---

### 项 6. (撤销) CandleLayer 业务数学下沉

**结论**:撤销此项。

**原因**:
- CandleLayer 中 `bodyWidth` 计算依赖 `PlotArea.Width`,而 `PlotArea` 是布局结果,Feature 在 `OnProject` 阶段不应感知具体像素;强行下沉会把 PlotArea 也塞进 Feature,反而破坏隔离
- 像素空间几何(居中、padding、抗锯齿对齐、视口剔除)本就是 Layer 的天职,不属于"业务数学"
- "图层=纯指令录制器"应理解为 **Layer 不做业务判断(涨跌阈值、K线合并、统计) 与 数据加工**,而不是禁止任何运算

**修订原则**:像素空间布局留在 Layer;业务语义留在 Feature。原架构文档 §5 步骤 C 的措辞过严,后续可在文档侧补充更精确的边界说明(此项不在本方案落地范围)。

### 项 7. Renderer 主循环改派发表

**现状**:`Renderers/DrawingRenderer.cs:43-174` 是 16-case 单体 switch,新增 DrawOp 要改 WPF + Skia 两处。

**改动方案**(WPF/Skia 同构)
1. 静态构造期注册:
   ```csharp
   private static readonly Action<WpfDrawingRenderer, DrawCmd, DrawingContext>[] _ops 
       = new Action<...>[16];
   static WpfDrawingRenderer() {
       _ops[(int)DrawOp.DrawLine]      = (r, c, ctx) => r.DrawLine(c, ctx);
       _ops[(int)DrawOp.DrawRectangle] = (r, c, ctx) => r.DrawRect(c, ctx);
       // ...
   }
   ```
2. 主循环:`_ops[(int)cmd.Op](this, cmd, context);`

**验收**
- 主循环长度 < 20 行
- 新增 DrawOp 仅改 enum + 注册一个 Action,主循环零改动

---

### 项 8. CompositeChartLayer 缓冲职责文档化

**现状**:`Core/CompositeChartLayer.cs` 有自己的双缓冲,同时通过 `Append` 合并子层指令,**子层是否需要自己 Buffer**未文档化,容易误用。

**改动方案**
1. 在 `CompositeChartLayer` 类头加 XML 注释明确:
   - 子层不分配 front/back,只输出指令到一个临时 `DrawingBuffer`
   - 父层负责 swap
2. 新增 `IChildLayer`(无双缓冲版本),让 `Add(IChildLayer)` 强类型约束
3. 现有 `IChartLayer` 仅供顶层使用

**验收**
- 误把顶层 Layer 当子层 Add 时编译期报错

## P2 — 健壮性 / 锦上添花

### 项 9. VisualDataBag._changedIds 生命周期治理

**现状**:`_changedIds` 只在 `Clear()` 清空,长期复用 Bag 而不调 Clear 会累积。

**改动方案**
- `CommitFrom` 完成后自动 `_changedIds.Clear()`
- 或在 `Publish` 时检测重复 ID 不再追加

---

### 项 10. VisualDataBag 数组增长封顶

**现状**:`_repo` 按 `+16` 增长无上限。

**改动方案**
- 设硬上限 `MaxTraitTypes = 1024`,超过即 `throw new InvalidOperationException("trait 类型注册过多,可能存在泛型滥用")`

---

### 项 11. Trait → Layer 编译期 / Compose 期强校验

**现状**:`data.Get<T>()` 缺则返回 null,Layer 静默 return,运行时静默失效。

**改动方案**(依赖 Roslyn 生成器)
1. 在 Layer 上加 `[RequiresTrait(typeof(CandleData))]` 标注
2. PortGenerator 扩展:为每个 Layer 生成 `_RequiredTraits.g.cs`,包含必需 trait 列表
3. `OnCompose` 阶段 ChartCell 校验:Layer 所需 trait 是否有 Feature 在写入,缺则抛

**验收**
- 漏写 Feature 时,启动即报错并指出"`CandleLayer` 需要 `CandleData`,但无 Feature 发布"

---

### 项 12. CandleLayer 跨帧复用列表

**现状**(`Layers/CandleLayer.cs:92-95`)每帧 `new List<HevoRect>`,虽预分配 capacity,但首次仍分配。

**改动方案**
- 提升为 Layer 字段:
  ```csharp
  private readonly List<HevoRect> _upRects = new(256);
  private readonly List<HevoRect> _downRects = new(256);
  private readonly List<HevoPoint> _wicks = new(512);
  ```
- 每帧开头 `Clear()`,末尾使用

**验收**
- 稳态 Gen0 = 0(配合项 1)

## 3. 衡量指标

落地后需在样例图(`Hevo.Drawing` Sample)上验证:

- **0-GC**:稳态 60s 内 Gen0 = 0(BenchmarkDotNet `MemoryDiagnoser`)

- **契约失效**:漏写 Feature 时启动期能 fail-fast(非渲染期)
