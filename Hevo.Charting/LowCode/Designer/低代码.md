# 低代码蓝图设计

> 由 JSON 蓝图在运行时动态孵化 `ReactiveSchema` 的能力。
> 实现位于 `Hevo.Charting/LowCode/Designer/`,由 `ChartBlueprint` + `DynamicChartSchema<T>` + `ComponentRegistry` + `SmartActivator` + `ComponentMetadataRegistry` + `BlueprintRunner` 六件套构成。
>
> JSON 序列化标准入口:[BlueprintJsonOptions.Default](Converters/BlueprintJsonOptions.cs) —— 蓝图持久化走这份 options(注册了 Color / IHevoBrush 多态 Converter + NaN/Infinity 数字策略),不要每个调用点 new 一份。

## 0. 当前架构(2026-05-08 重构后)

### 现行架构

| 组件 | 文件 | 职责 |
|---|---|---|
| `PlotFeature`(统一 series 协议) | [PlotFeature.cs](../../Features/PlotFeature.cs) | 单一容器:`Series: PlotSeriesSpec[]`,每 spec 按 `Kind` (`line`/`bar`/`scatter`/`arrow_markers`) 派子 Feature。Indicator 委托返 dict;line/bar 走旧 dict-shape ROM<double>,scatter/arrow 走 list[dict] |
| `PlotSeriesSpec` | 同上 | record:Name + Kind + Color + Width + 可选 XDomain/YDomain (RealRange?) for scatter |
| `ElementPlotFeatureBase<TSpec, TLayer>` | [ElementPlotFeatureBase.cs](../../Features/ElementPlotFeatureBase.cs) | scatter/arrow 共同基类:Spec 输入端口 + 鼠标 hit-test + ElementHovered/Doubled events + 可选 HitStatePort 写 PointerHitState 联 Tooltip |
| `ScatterPlotFeature` | [ScatterPlotFeature.cs](../../Features/ScatterPlotFeature.cs) | 散点 child Feature,XDomain/YDomain 显式 → publish layer-local XAxis/YAxis;留空 inherit 主图 axes |
| `ArrowMarkerFeature` | [ArrowMarkerFeature.cs](../../Features/ArrowMarkerFeature.cs) | 箭头 marker child Feature,固定 inherit 主图 axes |
| `ScatterPlotLayer` / `ArrowMarkerLayer` | [ScatterPlotLayer.cs](../../Layers/ScatterPlotLayer.cs) / [ArrowMarkerLayer.cs](../../Layers/ArrowMarkerLayer.cs) | 渲染层。消费 PlotAreaTrait + XAxisTrait + YAxisTrait + Spec trait |
| Spec 类型 | [PlotSpecTraits.cs](../../Core/PlotSpecTraits.cs) | `ScatterPoint(X, Y, Size, Color)` / `ArrowMarker(LogicalX, LogicalY, Direction, Color, Size)` —— **纯渲染字段**,无 HoverText/ClickPayload metadata。业务 hover/click 通过 Index 反查自家数据 |
| `PlotElementEvent<T>` | [PlotElementEvent.cs](../../Features/PlotElementEvent.cs) | `(int Index, T Element)` 强类型 record struct,无 metadata 字段 |

### 关键设计决策

1. **scatter/arrow 是 PlotFeature 的 Series kind**,不是独立顶层 feature。跟 line/bar 平级,用同一统一协议
2. **Spec 类型只含渲染字段** —— `HoverText`/`ClickPayload` 这种 Python 协议 metadata 不绑进框架。业务 hover/click 拿 Index,从自家数据表反查 metadata
3. **`@register_plot` Python 装饰器已删除** —— 框架只保留 `@register`(typed ROM<double> handler)和 `@indicator`(多 series 元数据)。plot handlers 走 `PythonHandlerRegistry.RegisterPythonFunction(name, file, fn, inputs)` 手动登记成 untyped `Func<object?[], object?>`(返 list[dict])
4. **PlotFeature `HitStatePort: DataPort<PointerHitState?>?`** 透传给 child element feature,用于跟 `TooltipWidgetFeature<TX>` 联动。tooltip 接 PlotFeature.HitStatePort 即可显示 hover 信息
5. **Tooltip 默认行**:XAxisDataPort + XMeta 出第一行;layer-side 的 MetaTrait + DoubleSeriesDataTrait 自动捞为后续行。scatter/arrow 默认 NOT publish 这俩 trait — 业务想要更多 tooltip 行可单独加 Feature publish

## 0.1 框架约定 (2026-05-08 落地)

### 蓝图运行路径反射零开销 — `IBlueprintRunnable`

[BlueprintRunner.cs](BlueprintRunner.cs) 同文件定义,`DataSource<TSource, TItem>` 基类自动实现:

```csharp
public interface IBlueprintRunnable
{
    object RunBlueprint(ChartCell chart, ChartBlueprint blueprint, BlueprintHandlerRegistry? handlers = null);
    object BuildBlueprintSchema(ChartBlueprint blueprint, BlueprintHandlerRegistry? handlers = null);
}
```

业务侧 caller(`BlueprintEditorView.Apply` / `BlueprintLauncher.LaunchInternal` / `DashboardLauncher.BuildCellSchema`)拿到 `object` / `IBlueprintRunnable` 引用直调,**不要再写**反射 5 段桥(`dsType.GetProperty("Stream") + GetMethods + Where + MakeGenericMethod + Invoke`)—— 之前每个 caller 自己复制一份,演化时签名漂移要同步多处。统一接口后调用点零反射,签名漂移由编译器抓。

新增同款需求(将来如 trigger 节点)按此模式扩;99% 直接派生 DataSource,IBlueprintRunnable 自动覆盖。

仍然合理的反射(JSON → Type → 实例化阶段,不要误清):
- `ComponentRegistry.Resolve("TypeName")` — JSON 字符串 → Type
- `SmartActivator.InjectProperties` — Properties dict → 字段 setter
- `BlueprintLauncher.DryRun` 里 `FindDataSourceItemType` — 静态校验阶段没 ds 实例
- `Seed<T>` trait 播种 — 已用 Expression 编译缓存 38ns/次,改 ITraitSeedable 每个 trait 加样板 ROI 太低
- `ConsoleDebuggerFeature` `board.Read<T>` — 调试雷达专用

### 错误处理:配置错就 throw,环境错才 Trace

**配置错误**(蓝图作者写错 / 业务侧没注册 handler / 端口 wire 反了)→ **直接 throw**,fail-fast,让用户立刻看到。包括:
- `PlotFeature.OnCompose` 里 `Indicator == null && IndicatorName 非空` → throw
- `ComputeFeature.OnCompose` 里 `Compute == null` 且端口已接 → throw
- `DynamicChartSchema.ResolveHandlerReferences` handler 名查不到 / 类型不兼容 → throw

**环境/资源错误**(Python init 失败 / 网络拉取失败 / 文件不在)→ 用 `System.Diagnostics.Trace.TraceError` / `TraceWarning` 报。完整异常链(`ex.ToString()` 含 Python traceback) + 修法 checklist 一并摊在 Trace 输出。VS Debug Output 默认显,业务侧 app.config 加 TraceListener 转写 file/网络/OTLP。**不要** `Console.WriteLine`(WPF 子系统 Console 默认看不见)。

不该做的:
- ❌ 不要在 demo Window 里弹 MessageBox 转译 framework 错误(分层错误)
- ❌ 不要把异常存字段让别处去查(Stage / ErrorDetail 这种被驳回过)
- ❌ 不要中央诊断聚合(Schema.Diagnostics 列表 + 事件订阅那种,被驳回过)
- ❌ 不要 Console.WriteLine

## 1. 蓝图模型(JSON Schema)

`ChartBlueprint` 的运行态结构(见 [ChartBlueprint.cs](ChartBlueprint.cs)):

```jsonc
{
  // 1. 数据源:类型名 + 字段→引脚 ID 的映射
  "DataSource": {
    "TypeName": "TimeShareDataSource",
    "ScalarMappings": {                  // 标量字段(单值上下文,从 DataSource 实例上反射取值)
      "PreClose": "Env_PreClose"
    },
    "VectorMappings": {                  // 向量字段(从 TItem 上反射取列,自动包成 ReadOnlyMemory<T>)
      "Time":  "RealTime_Time",

    }
  },

  // 2. 初始 Trait 播种:Schema 启动时一次性 Seed 进 Shared 域

  ],

  "Features": [
    { "TypeName": "PlotAreaDecorFeature", "Properties": { /* ... */ }, "PortBindings": { /* ... */ } },
    { "TypeName": "LineSeriesFeature",

```

## 2. 装配引擎

```csharp
var ds = new TimeShareDataSource();
BlueprintRunner.Run<TimeData>(host.Cell, blueprint, ds, ds.Stream);
// 等价快捷重载(自动接 ds.Stream)
BlueprintRunner.Run(host.Cell, blueprint, ds);
```

`DynamicChartSchema<T>` 三件事:

1. **`DefineDataFlow`** — 优先查 [`ComponentMetadataRegistry`](ComponentMetadataRegistry.cs):若数据源类型登记了自定义策略,整支管线交由策略接管。否则按 `ScalarMappings` 反射构造 `ContextIngestor<TItem,TSource,TValue>`、按 `VectorMappings` 反射构造 `ScatterIngestor<TItem,TValue>`,`StartWith(ds.GetSnapshot())` 灌首帧,`DoOnDispose(pipe.Dispose)` 收尾,`.BindTo(chart)` 注册主流。数据源若实现 `IDisposable` / `IPausable` 自动通过 `RegisterDisposable` 挂在 schema 生命周期上。
2. **`DefineFeatures`** — 遍历 `InitialTraits` Seed,遍历 `Features`:`ComponentRegistry.Resolve(TypeName)` 拿 Type → `Activator.CreateInstance` 实例化(要求 public 无参 ctor)→ `SmartActivator.InjectProperties` 注 Properties → `PortBindings` 把全局引脚焊到 Feature 的 `DataPort<T>` 字段(init-only 字段反射 SetValue 直接穿透)→ `canvas.Add(feature)`。
3. **全局引脚注册表** — 同一个 `portId` 在该 Schema 内全局唯一,跨 Feature 共享 `DataPort<T>` 实例。

## 3. 组件注册

```csharp
// 手动登记
ComponentRegistry.Register<LineSeriesFeature>();

// 反射批量登记(推荐)
BuiltinRegistration.RegisterBuiltins();
BuiltinRegistration.RegisterAssemblyOf<TimeShareDataSource>();
```

收录条件(详见 [BuiltinRegistration.cs](BuiltinRegistration.cs)):
- ChartFeature:public、非抽象、非泛型定义、有 public 无参 ctor。`AxisFeature` 因 ctor 需 `ITickProvider` 不会被自动登记 —— §7.5 已用无参 ctor + init 属性铺平。
- IVisualTrait:public、非抽象、非泛型定义。无参 ctor 不强制(record 走 Preset)。
- DataSource:沿继承链找 `DataSource<,>`。

未注册的 `TypeName` 在 Resolve 时直接抛"未知组件类型"异常。`Resolve` 支持 `prefix:TypeName` 形态查找(精确匹配失败 → 回退查无前缀名,详见 §B11 alias prefix)。

## 4. 性能优化代理(`ComponentMetadataRegistry`)

图形引擎 60 FPS 百万级渲染对特定业务流(如 A 股分时图 240 点)采用**预分配数组占位**(`BindIndexedColumn`)。这种内存优化绝不能反向污染 JSON 蓝图,否则低代码用户得理解列式存储。

蓝图编译期发现某 `DataSource` 类型在元数据表里登记了 `IPipelinePolicy`,编译器自动接管该数据源的管线装配,**蓝图层零感知**。

```csharp
public class TimeShareIndexedPolicy : PipelinePolicy<TimeShareDataSource, TimeData>
{
    protected override void CompileTyped(
        ChartBlueprint blueprint, TimeShareDataSource ds,
        UniversalDataPipe<TimeData> pipe, Func<Type, string, object> getOrCreatePort)
    { /* 走预分配数组占位的高性能装配路径 */ }
}

ComponentMetadataRegistry.Register<TimeShareDataSource>(new TimeShareIndexedPolicy());
```

戒律:
- ❌ 禁止在蓝图模型(JSON)里暴露性能相关参数(如 `IsFixedLength`)
- ✅ 必须在 `ComponentMetadataRegistry` 里登记 DataSource 的管线编译策略

## 5. SmartActivator 物化策略

[`SmartActivator.MaterializeTrait`](ComponentRegistry.cs):

| StyleModel 配置 | 行为 |
|---|---|
| 仅 `Properties` | `Activator.CreateInstance(type)` + `InjectProperties` (传统 POCO) |
| 仅 `Preset` | 取 `type` 上 public static 字段/属性,直接复用单例 |
| `Preset` + `Properties` | 取预设实例后再覆盖部分字段(record 路径走 `<Clone>$` 避免污染共享单例,§B6) |

`InjectProperties` 已支持 `JsonElement` 降级、Enum 字符串、`Nullable<T>`、`TypeConverter`、`IConvertible` 五重兜底;setter 不是 `public` 的属性(`internal set` / `private set`)一律视为框架托管字段,蓝图 Properties 即便挟带同名 key 也不写入(§F)。

## 7. 可视化拖拽编辑器(GraphViewer)

> 实现位于 [`Hevo.Charting/LowCode/Designer/GraphViewer/`](GraphViewer/),业务侧入口
> [`GraphViewerBootstrap.Initialize()`](GraphViewer/GraphViewerBootstrap.cs)。

### 7.1 架构概览

GraphViewer 是 `ChartSchema` 的子类(**非 ReactiveSchema**),纯像素坐标系,5 层渲染管线:

| 层 | Z 槽位 | 职责 |
|---|---|---|
| `GraphCanvasLayer` | Background | 底色 + 自适应网格 + **类别泳道**(按节点 Y 范围动态合并) |
| `GraphEdgeLayer` | Main | 贝塞尔连线(WPF 端走 `StreamGeometryContext.BezierTo` GPU 抗锯齿) |
| `GraphNodeLayer` | Main | 圆角矩形 + 标题栏 + 端口圆点(扇入端口画方块,字尾 `[]`) |
| `GraphSelectionLayer` | Selection | 选中描边 + 框选橡皮筋 |
| `GraphPreviewLayer` | Interaction | 拖出连线橡皮筋 + 端口悬停 tooltip |

5 层共享同一个 `GraphRenderTrait(GraphState)` 实例 — `GraphState` 引用换新一发,`VisualDependencyTracker.CheckIfDirty` ReferenceEquals 一击命中,所有 layer 同帧 MarkDirty 重画。

### 7.2 数据模型

```csharp
record GraphState(

```

任何变更都走 `state with { ... }` 出新引用。`AddEdge` 对扇入端口允许多 incoming,普通端口覆盖。

### 7.4 蓝图协议扩展

[`ChartBlueprint.cs:DefineFeatures`](ChartBlueprint.cs) 现支持两种 port 形态:

| 形态 | JSON | 后端解析 |
|---|---|---|
| 单 `DataPort<T>` | `"DataPort": "global_price_id"` | `GetOrCreatePort` + 反射 SetValue |
| `DataPort<T>[]` 扇入 | `"ValuePorts": ["id1","id2","id3"]`(B8 数组化)/ 兼容老 CSV | 拆数组 → 逐个 GetOrCreatePort → 反射写数组 |

[`GraphSerializer.ToBlueprint`](GraphViewer/GraphSerializer.cs) 关键点:
- 检测 `Port.IsArray`,扇入端口所有 incoming edges 用数组形态写出
- **每个 Feature 自己的 OUTPUT 端口也写 PortBindings 字段**(否则 `UniversalAutoScale.YRangePort` 这种 init=null 字段一直 null,Watch NRE 静默吞,axis/grid/line 全黑)
- DataSource 节点 `Properties` 字典除 `ScalarMappings/VectorMappings` 外的字段进 `bp.DataSource.Properties`,运行时 `SmartActivator.InjectProperties` 注入

#### 7.4.1 端口类型严格化

[`DynamicChartSchema.GetOrCreatePort`](ChartBlueprint.cs) 类型严格版,签名 `object?`:同一 portId 已被以另一个 T 注册过 → 返回 null + warning,不返回脏类型让 ctor 抛 ArgumentException。三处调用方(`CompileScalarMappings` / `CompileVectorMappings` / `DefineFeatures.PortBindings`)统一 null-check + skip。`IPipelinePolicy` 路径走 `?? throw`(对策略类型已知,冲突算 bug)。

`ScatterIngestor` 反射 ctor 改用 `ConstructorInfo.Invoke`(`Activator.CreateInstance` 对 `null` arg 类型推断会失败)。

#### 7.4.2 Viewport 节点

`Viewport.LogicalLength` / `UserRange` / `ActiveRange` 是 schema 内部 ports,但**蓝图必须显式连**。引入 [`NodeKind.Viewport`](GraphViewer/GraphState.cs) + [`NodeFactory.CreateViewportNode`](GraphViewer/NodeFactory.cs):Viewport 节点不对应任何 .NET 类型,GraphSerializer 检测 edge 末端是 Viewport → globalId 强制走 well-known id (`VP_LogicalLength` / `VP_UserRange` / `VP_ActiveRange`);DataSource ScalarMappings 同步覆盖;`DynamicChartSchema` 构造时预登记 → 任何使用 well-known id 的端口拿到的就是 schema 自己持有的 ViewportPorts 实例,**不创建副本**。

## 8. 关键 fix 历史(简要)

> 详细前后文见 git log,这里只列防止重蹈的关键决策。

1. **GraphSerializer 漏写 OUTPUT 端口绑定** → 每个 Feature 序列化时自家 OutputPorts 也写 `PortBindings`,跟下游 input 共享同一全局 portId
2. **DynamicChartSchema 漏写 Viewport.LogicalLength** → 升级成 Viewport 节点 + well-known id,蓝图侧画一根线显式表达

4. **端口类型 cache 冲突** → §7.4.1 类型严格化
5. **Edge 渲染同 source 多线视觉重叠** → 计数偏移 ±8*N px;贝塞尔反向边 dx 强化防"S 钩"
6. **Edge 被中间 node 遮挡** → `GraphEdgeLayer` 移到 `GraphNodeLayer` 之上;`ComputeAvoidanceVOffset` 控制点绕开节点;双笔渲染(深色 outline + 亮色 EdgePen)
7. **AutoLayout 列分组 → 类别横幅全重叠** → 改成横向泳道,`ComputeDepth` Kahn 拓扑序排 col,任何 edge 天然 a.col < b.col 消除反向钩
8. **连线像折线** → 加 `DrawOp.DrawCubicBezier` 原生贝塞尔指令([Primitives.cs](../../Renderers/Primitives.cs)),WPF 端走 `StreamGeometryContext.BezierTo`
9. **JSON 预览/导入对 NaN/Infinity 炸** → 共享 `JsonSerializerOptions` 加 `NumberHandling = AllowNamedFloatingPointLiterals`(已统一进 `BlueprintJsonOptions.Default`);NodeEditorWindow TextBox 路径加 `IsSpecialFloat` 判断按空串显示

### 演进路径:Role enum → Links 数组

**老实说**:Role enum 是工程妥协(简单场景够用),不是设计胜利。下面这些场景 Role 撞墙,Links 数组协议天然解:

| 撞墙场景 | Role 行为 | Links 协议解 |
|---|---|---|
| 双策略并列对比(A 主+副、B 主+副,A↔B 不联动) | ❌ SharedHit 全 Master/Pane 都连上,无法隔离 | `{Kind: ViewportShared, Cells: [a-main, a-vol]}` + 另一组 `{...Cells: [b-main, b-vol]}` 独立 |
| 多时间尺度联动(1m 主图 + 5m 副图共享时间区间但 logical index 不同) | ❌ SharedViewport 默认 LogicalLength 共享,index 不齐崩 | `{Kind: TimeRangeShared, Axis: TimeStamp}` 新 Kind |
| 共享 X 轴但不共享 crosshair(pan/zoom 同步,十字线独立) | ❌ 二选一,Master/Pane 绑死 | 给一组 cell 加 ViewportShared 不加 CrosshairLinked |
| 业务自定义高亮(cellA 点击 → cellB 高亮关联) | ❌ | `{Kind: SelectionLinked}` + 业务派 ILinkResolver 子类 |
| 单 cell 参与多条 link(策略对比 + 全图 X 轴对齐) | ❌ Role 是单值 | cell.Id 出现在多条 link 里 |
| Link 自带参数(节流毫秒 / 颜色映射) | ❌ enum 不带参 | `{..., Properties: {throttleMs: 100}}` |

**触发迁移的业务信号**(任一出现就开搞):
- 多策略对比需求(双盘并列、回测对比)
- 跨时间尺度联动(分钟 + 日线同图)
- 业务方提出自定义 link 类型(SelectionLinked / AnnotationSync 等)

**迁移方案(~2-3d)**:

1. 加 [`DashboardLinkModel { Kind, Cells, Properties }`](Dashboard.cs) 数据结构;`Dashboard` 加 `Links: List<DashboardLinkModel>`
2. `ILinkResolver` 抽象 + 内置 `ViewportSharedResolver` / `CrosshairLinkedResolver`(等价于现在 `LinkedChartContext` 拆成可组装的小模块);业务派 ILinkResolver 子类自定义新 Kind
3. DashboardLauncher 装配阶段遍历 Links → 调对应 Resolver → 在涉及 cell 间建端口镜像桥
4. DryRun:`BP_DASHBOARD_BAD_LINK`(cell id 不存在 / 同一 cell 两次同 Kind 冲突)
5. **老 Role 字段保留兼容**,装配时 desugar 成 Links 形态(`Master+Pane` → `{Kind: ViewportShared, Cells: [所有 Master+Pane]}` + `{Kind: CrosshairLinked, Cells: [所有 Master+Pane]}`),老蓝图加载不破
6. LinkInspector UI:列表展示 + 增删 + cell 多选

**为什么不立即做**:Links 是"一种灵活性预算",没出现真实需求就提前付代价 = 过度设计。当前业务全是单图 / K线主+副,Role 够用。把演进路径写在这里,未来碰到上述触发信号时不必从零设计,照着 1-6 步走即可。

### D2.6.4 IIncrementalCompute 增量协议 ✅ 已交付(2026-05)

EMA / RSI / Kalman 滤波这类指标内部有**累加器状态** —— 每个 tick 派生 O(1) 而非每帧重算 O(N) 全窗。当前 `ComputeFeature` 路径每帧把 close 全数组喂进 `Func<ROM, ROM>`,handler 内部自己 `np.convolve` —— 240 点 EMA 实测 ~3μs/帧,5000 股扫描线性放大到 15ms/帧, 60Hz 已破帧。增量协议把"上一帧 state"显式在 wire 上,handler 只看新到点 + prev_state 算 next_state + 增量输出,O(1) 派生。

> **触发线**:E1 5000 股 + Top-N 多输入指标场景 profile 出 ComputeFeature 是热点时落地;单股 demo 不必做。原型先就位,业务真撞墙时拿出来用。

#### D2.6.4.1 协议层(三个工程决策)

**决策 1 — state 装哪里?Feature 内部 private 字段(不入 board 端口)**

考虑过两条路径:
- **A. State 在 board 端口**(原一稿设计):portId 显式 wire,蓝图 PortBindings 必填 StatePort。优点是"D3 Remote 天然适配"。
- **B. State 装 feature 内部 `private ReadOnlyMemory<double> _state` 字段**(终选):蓝图协议简洁(只 InputPort + OutputPort 两根),无 PortBindings ceremony,无反馈环概念。

**最终选 B**,理由:
- 把 D3 Remote 的诉求**前置**到 D2.6.4 是过度设计 —— D3 还在 ⚙️ 状态,真到 Remote 时 `RemoteIncrementalComputeFeature` 子类自己 serialize `_state` 进 RPC 入参,跟 board 端口路径**等价**(state 装哪不影响 RPC 接力语义)
- 每个 IncrementalCompute 实例自带 state,**根本上排除**"两个 feature 共享 portId 串味"这种隐患 → 一整条 DryRun 错误码(`BP_PYHANDLER_INCREMENTAL_STATE_SHARED`)和`BP_PYHANDLER_INCREMENTAL_NO_STATE_PORT` 不复存在
- 业务侧 schema.Add 时不需要"必填 StatePort 全局唯一 portId"心智负担
- schema lifetime ≡ state lifetime —— schema 重建即丢 state(典型场景:重连数据源 / 切 symbol),刚好是预期语义。真要"暖热不丢"是 D3 业务范畴,核心库不背

**决策 1.5 — 单类双模式(单输入 + 多输入合一),非新派子类**

ATR-stateful / OBV-stateful 这类多输入 + state 指标,跟 ComputeFeature 多输入对齐:同一个 `IncrementalComputeFeature` 加 `Inputs: Dictionary<string, DataPort<ROM>>` + `InputOrder: string[]`。`Inputs.Count > 0` 走多输入路径,空则走单输入。

否决"派 `IncrementalMultiInputComputeFeature` 子类"的理由:跟 ComputeFeature 模式一致(它也是单类双模式);DryRun 一处 IsAssignableFrom 覆盖所有派生;蓝图 / GraphSerializer / NodeFactory 元数据都不需要再加新类型。代价是 OnCompose 内部 if/else 一次,可读性 OK。

**handler 形参约定**:state 是**隐含的最末位形参**,**不**出现在 `InputOrder` / Python `inputs=[...]` 列表里。两侧都只列数据输入:
- 单输入 EMA:`Func<ROM, ROM, (ROM, ROM)>` → 形参 `(close, prev_state)`
- 多输入 ATR:`Func<ROM, ROM, ROM, ROM, (ROM, ROM)>` → 形参 `(high, low, close, prev_state)`,Python `inputs=['high','low','close']` 不含 state

**决策 2 — handler 签名仍带 prev_state 形参**

虽然 state 装 feature 字段,handler 签名**不变**:仍是 `Func<ROM, ROM, ValueTuple<ROM, ROM>>`,形参 `(input, prev_state)` 返回 `(output, next_state)`。

这样保留两个好处:
- handler 是**纯函数** —— 测试 / mock 友好,不依赖 schema 状态
- D3 Remote 路径上,handler 形参 `prev_state` 自然成为 RPC 入参,无需为 Remote 重设计签名
- feature 内部只是把字段值喂给 handler 形参 + 接住返回值更新字段,thin shim

```csharp
// IncrementalComputeFeature.OnComputeCompose 关键骨架(决策 1+2 后)
flow.Watch(new object[] { InputPort }, board => {
    var input = board.Read(InputPort);
    var (output, nextState) = handler(input, _state);     // _state 是 feature 字段
    _state = nextState;                                    // 单线程 watcher 串行,无并发
    board.WriteIfChanged(OutputPort, output);
});
```

**handler 必须自处理首帧**:state.Length == 0 → bootstrap(用 input[0] 当 prev,或返回空 output 等下一帧)。这是约定,核心库不替 handler 决定。

**决策 3 — 字段加在 `ComputeFeature` 还是新派 `IncrementalComputeFeature`?新派(non-sealed)**

ComputeFeature 已撑了"单输入 + 多输入(`Inputs` 字典 + `InputOrder`)"两形态,字段数已临界。再塞 `IsStateful` + handler 签名分支:
- OnComputeCompose 三层 if/else,可读性塌
- IsStateful=true 时 Compute 委托类型从 `Func<ROM,ROM>` 变 `Func<ROM,ROM,ValueTuple<ROM,ROM>>`,委托身份强相关,DynamicInvoke 路径必须新分支

新派 `IncrementalComputeFeature : ComputeNodeFeature`(跟 ComputeFeature 平级而非子类),**non-sealed** —— 业务可派生 `EmaFeature(int length) : IncrementalComputeFeature` 把 length / alpha 参数化进 ctor,DryRun 走 `IsAssignableFrom` 自动覆盖派生类(决策 4)。

**决策 4 — DryRun 类型识别用 `IsAssignableFrom`,不用字符串名匹配**

否决早期 `featureType.Name == "IncrementalComputeFeature"` 字符串匹配,理由:
- 派生子类 `MyEmaFeature : IncrementalComputeFeature` Name 不等 → 错过 DryRun 校验 → 运行时黑屏
- 重命名核心类 / 跨 assembly 同名都会失配

实装走 `typeof(Hevo.Charting.Features.IncrementalComputeFeature).IsAssignableFrom(featureType)`,BlueprintLauncher 跟 IncrementalComputeFeature 同 assembly 直接引用。派生子类天然受保护。

#### D2.6.4.2 Python 端 API

```python
# indicators/ema.py
import numpy as np
from hevo_indicators import register

@register('ema_20',
          incremental=True,                                              # ← 关键 kwarg
          signature='(ReadOnlyMemory[double], ReadOnlyMemory[double]) -> Tuple[ReadOnlyMemory[double], ReadOnlyMemory[double]]')
def ema_20(close, prev_state):
    """EMA-20 增量。close 是当前帧全量 close 数组;prev_state 是 length-1 数组 [prev_ema]。"""
    alpha = 2.0 / (20 + 1)
    if prev_state.size == 0:
        prev = close[0]                                                   # ← 首帧 bootstrap
    else:
        prev = prev_state[0]
    new_ema = close[-1] * alpha + prev * (1 - alpha)
    output = np.array([new_ema])                                          # ← 当前帧增量结果
    next_state = np.array([new_ema])                                      # ← 下一帧的 prev
    return output, next_state                                             # ← Python tuple → C# ValueTuple

# 多输入 + stateful (ATR-stateful) — 复用 §D2.X 多输入约定
@register('atr_14_stateful',
          incremental=True,
          inputs=['high','low','close'],
          signature='(ROM[double], ROM[double], ROM[double], ROM[double]) -> Tuple[ROM[double], ROM[double]]')
def atr_stateful(high, low, close, prev_state):
    ...
```

**协议要点**:
- `incremental=True` 时 signature 必须是 `Tuple[ROM[double], ROM[double]]` 返回(`(output, state)` 二元组)
- Python tuple → C# `ValueTuple<ROM, ROM>` 由 PythonMarshaller 处理(已支持单 ROM,加 ValueTuple 解包是边际工作)
- 无 incremental kwarg = 走现有 ComputeFeature 路径,完全向后兼容

#### D2.6.4.4 业务侧非蓝图用法(C# 直接 schema.Add)

**单输入** —— 强类型 `StatefulCompute` init 属性,**无需** ValueTuple<,> 拼写或 Delegate 字段强转:

```csharp
schema.Add(new IncrementalComputeFeature {
    InputPort       = closePort,
    OutputPort      = emaOutPort,
    StatefulCompute = (close, prev) => {
        var alpha   = 2.0 / (20 + 1);
        var prevVal = prev.Length == 0 ? close.Span[0] : prev.Span[0];   // 首帧 bootstrap
        var newEma  = close.Span[^1] * alpha + prevVal * (1 - alpha);
        var arr     = new[] { newEma };
        return (arr, arr);    // ← C# 9 tuple literal,自动 conv 到 ValueTuple<ROM, ROM>
    },
});
```

**多输入** —— 走 `Compute` Delegate 字段(arity 不固定不便给 typed 属性,业务自己写 typed Func):

```csharp
schema.Add(new IncrementalComputeFeature {
    Inputs     = new() { ["high"]=highPort, ["low"]=lowPort, ["close"]=closePort },
    InputOrder = new[] { "high","low","close" },
    OutputPort = atrOutPort,
    Compute    = new Func<ROM<double>, ROM<double>, ROM<double>, ROM<double>,
                          (ROM<double>, ROM<double>)>(
        (h, l, c, prev) => {
            var hi = h.Span[^1]; var lo = l.Span[^1]; var cl = c.Span[^1];
            var prevClose = prev.Length == 0 ? cl : prev.Span[0];
            var prevAtr   = prev.Length == 0 ? hi - lo : prev.Span[1];
            var tr  = Math.Max(hi - lo, Math.Max(Math.Abs(hi - prevClose), Math.Abs(lo - prevClose)));
            var atr = (prevAtr * 13 + tr) / 14;          // Wilder length=14
            return (new[] { atr }, new[] { cl, atr });
        }),
});
```

**关键决策**:

- **PythonInvokerShim 已是 N-arity 通用**(读 `TDel.Invoke` 的 `ParameterInfo[]` 数组动态构建 args[] expression)— PythonTypeMapper.ResolveDelegateType 也走 `Expression.GetFuncType` 支持任意 arity 到 16 参,无需为多输入新增代码。
- **Compute 字段类型从 `Func<X,Y>?` 升级到 `Delegate?`**:单输入 + 多输入 + Action(handler 副作用)统一接口。`ResolveHandlerReferences.IsAssignableFrom` 仍生效(`Delegate.IsAssignableFrom(Func<...>) = true`),业务 C# 直接注入 `Func<ROM,ROM>` 也无破坏。单输入路径有热路径优化:`Compute is Func<ROM,ROM> typed`(避免 DynamicInvoke 装箱)。
- **InputOrder 用单独字符串数组**,而非"Dictionary 隐式按声明顺序"—— `Dictionary<string,...>` 顺序不是契约,InputOrder 显式为 source-of-truth。蓝图 JSON 写在 Properties 里,Python 端 `inputs=['h','l','c']` 跟 InputOrder 同语义。
- **NodeFactory 不主动嗅 indicator 元数据**:dict 字段在 ScanPorts 跳过,展开走 `ExpandInputSlots` 显式 API。picker 端要展开节点时由调用方传 inputs 列表(典型来源:`@indicator` 的 series 元数据,或业务自己塞)。这避免 NodeFactory 跨 PythonNet 层依赖。

**测试**(46 用例总绿):

- Scanner: `inputs=[...]` 字面量被正确捕获 / kwarg 顺序 / 缺失时为 null
- BlueprintHandlerRegistry: GetInputNames 注册查询 / Unregister 清理 metadata
- BlueprintRoundTrip: nested key `Inputs.high` 反序列化展开 child port → round-trip 后保留
- DryRun: 缺 PortBindings 报 BP_PYHANDLER_INPUT_UNCONNECTED;缺 InputOrder 报 BP_PYHANDLER_INPUT_ORDER_MISSING

- 不做"在编辑器内嵌 Python IDE"(分析师用 VS Code / PyCharm)
- 不做"完美沙箱"
- 不嵌入 Python runtime 跨 distribute(用户机器要自带 Python 3.x)
