# 新增业务组织编排模型

本文档定义在新框架下新增业务图表时的标准组织方式，目标是让业务代码保持统一结构，并能被 AI 与开发者稳定复用。

---

## 一、核心原则

新增业务图表必须以 `ReactiveSchema` 为唯一组合根。

标准结构不是“一个大类里什么都做”，而是把业务拆成四层：

1. `DataSource`：数据获取与上下文切换
2. `DataPipe`：从业务实体投影到 `DataPort<T>`
3. `ReactiveSchema`：声明式装配图表
4. `ChartFeature`：仅承载标准 builder 无法覆盖的独立能力

---

## 二、标准目录结构

一个业务目录推荐包含：

- `Schema.cs`
- `DataSource.cs`
- `Ports.cs` 或 generator 对应声明文件
- 业务专属 `Feature.cs` / `Formatter.cs` / `Helper.cs`（仅在必要时）

推荐形式：

```text
Hevo.Drawing/<Business>/
  Schema.cs
  DataSource.cs
  Ports.cs
  XxxFeature.cs       // optional
  XxxFormatter.cs     // optional
```

共享能力不要复制进业务目录，应沉到 `Hevo.Charting.Features` 或通用扩展中。

## 三、两阶段模型

### 1. `DefineDataFlow(ChartCell chart)`

职责只有四类：

- 接数据
- 投影/补充数据
- 路由到 `DataPort<T>`
- 绑定到 chart

典型形式：

```csharp
protected override IRenderFlow<DataBlackboard> DefineDataFlow(ChartCell chart)
{
    return _dataSource.Pipe()
        .ProjectExtent(_viewportPorts)
        .LinkStream(cfg => cfg.AutoMap())
        .BindTo(chart);
}
```

允许在此阶段做：

- `ProjectExtent(...)`
- `Inject(...)`
- `ForwardTo(...)`
- `LinkStream(...)`
- `AutoMap()`
- `BindTo(chart)`

不建议在这里混入视觉编排或业务 UI 决策。

### 2. `DefineFeatures(IFeatureContext canvas)`

职责只有一件事：把图表按结构化 builder 编排出来。

---

## 四、四段式 builder 编排

### 1. `Environment`

负责：

- `SetupLayout(...)`
- `SetupViewport(...)`
- `SetupAutoScale(...)`
- decor/header/背景/plot 辅助能力

### 2. `Axes`

负责：

- `AddDomainAxis(...)`
- `AddRangeAxis(...)`

### 3. `Series`

负责：

- `AddLine(...)`
- `AddBar(...)`
- `AddCandle(...)`
- 以及其它渲染序列

### 4. `Interactions`

负责：

- pointer
- crosshair
- tooltip
- keyboard
- paging / drag / hover 之类交互

标准示例：

```csharp
protected override void DefineFeatures(IFeatureContext canvas)
{
    canvas.Environment(env =>
    {
        env.SetupLayout(left: ChartLength.Pixel(70), right: ChartLength.Pixel(10), bottom: ChartLength.Pixel(24))
           .SetupAutoScale(_vp, _yRangePort, new[] { _valuePort }, paddingRatio: 0.1);
    })
    .Axes(axes =>
    {
        axes.AddDomainAxis(_timePort, _vp, _xMeta)
            .AddRangeAxis(_yRangePort, _yMeta, AxisPlacement.Left);
    })
    .Series(series =>
    {
        series.AddLine(_valuePort, _yRangePort, _yMeta);
    })
    .Interactions(interactions =>
    {
        interactions.EnableStandardPointer(_vp, _hitPort)
                    .AddCrosshair(_hitPort, _timePort, _xMeta)
                    .AddTooltip(_hitPort, _timePort, _xMeta);
    });
}
```

## 五、`OnCompose` 与 `OnProject` 的职责边界

### `OnCompose`

当前实现语义下，`OnCompose` 仍承担：

- workflow 挂载
- 事件订阅
- flow 变换
- 需要进入 compose 作用域的反应式连接

因此不要把它理解成单纯的初始化钩子。

### `OnProject`

`OnProject` 只负责读取并投影：

- 读取 `UsePort(...)`
- 读取 memo
- 发布 trait / 执行渲染相关投影

必须遵守：

- 不写黑板
- 不跨帧缓存 `UsePort(...)`
- `UsePort(...)` 顶层、无条件、固定顺序调用

---

## 六、Port 组织原则

### 优先 generator

适合 generator 的业务字段：

- 稳定字段集合
- 时间序列字段
- 数值序列字段
- DTO 直投影字段

推荐模式：

```csharp
[PortGroup("FinancePorts")]
public partial record FinanceItem
{
    [Port] public DateTime Time { get; init; }
    [Port] public double Balance { get; init; }
}
```

在 schema 中：

```csharp
.LinkStream(cfg => cfg.AutoMap())
```

### 保留手写的端口

下列端口通常继续手写：

- `ViewportPorts`
- `PointerHitState`
- `RealRange`
- 复杂组合对象
- 动态字段结构

---

## 七、动态更新协议

运行时需要替换字段、切换轴、增删序列时，必须使用：

```csharp
this.Transact(ctx =>
{
    // remove / add / recompose
});
```

原因：

- 保证轴、序列、交互原子更新
- 避免 UI 撕裂
- 让框架自动处理 feature 差异与订阅清理

---

## 八、新增业务的推荐开发顺序

1. 先定义业务 item / DTO
2. 判断哪些字段适合 generator
3. 写 `DataSource`
4. 写 `DefineDataFlow(...)`
5. 写 `DefineFeatures(...)`
6. 只有标准 builder 不够时，再新增 feature
7. 如果有动态重编排，再补 `Transact(...)`

---

## 九、给 AI 的最低约束

AI 在新增业务时必须遵守：

1. 不能回退到旧 `ChartPack + SeriesPack` 模式
2. 不能在 schema/feature 中直接处理原始 `TItem`
3. 不能跳过四段式 builder
4. 不能在 `OnProject` 写黑板
5. 不能跨帧缓存 `UsePort(...)`
6. 动态结构更新必须走 `Transact(...)`
7. 优先复用既有 schema 模式，不要自创组织方式

---

## 十、双源/多源时间对齐的组织模型

对于 `CelebrityEarning`、`HistoricalPeak` 这类双源对比业务，问题不在于框架缺少并流能力，而在于旧业务仍把“时间对齐 + 双流合并 + 结果投影”打包在 `PipeTimeUnion(...)` 风格里，导致新增业务难以复用统一模板。

### 1. 推荐的拆分原则

双源/多源业务仍然要遵守统一分层：

1. 每一路数据各自拥有独立 `DataSource`
2. 时间对齐属于数据流层，不属于 Feature 层
3. 对齐后的结果仍然要落到标准 `DataPort<T>`，而不是让 Feature 直接面对双源快照
4. `DefineFeatures(...)` 只消费对齐后的 ports，不感知底层并流细节

### 2. 当前仓库里的现实情况

当前仓库并不是没有并流能力：

- `Hevo.Charting/WorkFlow/TimeAligned.cs` 提供了 `PipeTimeUnion(...)`
- `Hevo.Charting/WorkFlow/FeatureExtensions.cs` 提供了 `CombineLatest(...)` / `Join(...)`

说明问题的本质不是“要不要支持并流”，而是要把并流表达从“业务直接依赖旧专用算子”收敛为“可被统一模板描述的数据流组织方式”。

### 3. 推荐的标准表达

对于双源时间对齐，推荐按下面的心智模型组织：

- `DataSource A`
- `DataSource B`
- `TimeAlignedPair` 或等价的对齐结果
- `DefineDataFlow(...)` 中完成：
  - 对齐
  - 对齐结果投影
  - `ProjectExtent(...)`
  - `LinkStream(...)`
  - `BindTo(chart)`

也就是说，双源图表的核心不是“两个图源直接喂给图层”，而是：

```text
SourceA + SourceB -> Time Align -> Aligned Result -> Ports -> Schema Features
```

### 4. 迁移约束

后续迁移 `PipeTimeUnion(...)` 业务时，必须遵守：

- 不把双源快照直接泄漏到 Feature
- 不在 Feature 中手写时间对齐逻辑
- 不把“时间对齐 + 渲染”揉在一起
- 默认优先直接把对齐结果投影到 ports；只有在业务语义明显失真的时候，才考虑额外声明新的中间结构

### 5. 迁移优先级建议

- 若某业务只是依赖 `PipeTimeUnion(...)` 做纯时间对齐，可进入并流专项迁移
- 若某业务同时耦合复杂模板/UI/动态配置，先拆模板，再拆并流
- 当前适合进入并流专项的代表对象：
  - `Hevo.Drawing/CelebrityEarning/Schema.cs`
  - `Hevo.Drawing/HistoricalPeak/HistoricalPeakSchema.cs`
