# Hevo.Charting / 业务 Feature 设计 & 开发手册

核心哲学：逻辑与物理分离，数据驱动渲染，极致 0-GC，事务级一致性。

## 🛡️ 架构铁律 (Developer Do's & Don'ts)

### 🚫 严禁越权管理容器法则
`PlotArea`（物理绘图区大小）是 `ChartCell` 的私有财产，业务特征绝不可越权干涉。
* **❌ 错误做法**：在 Feature 内部监听 `SizeChanged` 然后手动去算 `ActualWidth`。
* **✅ 正确做法**：`ChartCell` 会在底层自动将 `PlotAreaTrait` 写入共享上下文。业务 Feature 只需要使用 `Watch()` 监听事件触发重绘，然后去黑板（Blackboard）或 `ctx.Shared()` 里拔出 `PlotAreaTrait` 直接用即可。

### 🚫 严禁在 Project/Plot 中分配闭包 (0-GC 红线)
`Project` 是高频重绘帧，任何对象分配都会导致 GC 卡顿。
* **❌ 错误做法**：在高频重绘函数中直接使用局部外层变量（产生隐式闭包）。
* **✅ 正确做法**：依赖昂贵计算（如刻度生成、光标吸附搜索）时，必须且只能使用 `ctx.UseDynamicMemo("Key", deps, static (deps) => { ... })`。
  *(💥 注意：必须带上 `static` 关键字！底层利用 C# 9.0+ 编译器魔法，配合 static 可从物理层面禁止捕获外部变量，依赖不变时耗时绝对为 0，彻底消灭装箱与闭包 GC。)*

### 🚫 严禁散装配置 (The FieldMeta SSOT Rule)
交互特征涉及格式化、颜色、国际化名称时，严禁碎片化定义。
* **❌ 错误做法**：在组件中定义 `string XLabelFormat`, `Color TooltipColor`, `string AxisName` 等零散属性。
* **✅ 正确做法**：必须暴露 `FieldMeta? XMeta { get; init; }`，在 Schema 组装时将唯一的 `FieldMeta` 实例显式分发给所有相关组件，实现单点事实源强绑定。

### ✅ Compose / Project 职责切分
`OnCompose` 只负责挂载 workflow、事件订阅、图层注册和主 flow 变换；`OnProject` 只负责读取 `UsePort` / `UseMemo` 并发布 Trait。

- `OnCompose` 不再依赖返回 `IRenderFlow<DataBlackboard>`。
- 在 `OnCompose` 中如果要对主 flow 做变换，必须使用框架提供的 `flow.Watch(...)`、`flow.WatchAsync(...)`、`flow.Join(...)`、`flow.CombineLatest(...)` 等扩展，让变换进入统一 compose 作用域。
- `WithBoard(...)` 只负责把事件与当前黑板绑定；读写锁必须在事件处理内部显式获取。


# 🚨 DataBlackboard 与 UsePort 物理读取限制

在 V3.0 的 0-GC 极速渲染架构中，`DataBlackboard` 及其暴露的 `UsePort` / `Read` 方法是整个引擎的数据命脉。为了保证帧率与内存安全，所有业务 Feature 必须严格遵守以下四大物理限制：

## 1. 绝对禁止“跨帧缓存” (No Lifecycle Escape)
* **物理机制**：`UsePort` 提取出的数组（如 `ReadOnlyMemory<T>`, `Span<T>`）是底层复用内存的极薄切片。它们的生命周期**严格限定于当前帧的 `Project` 函数内部**。
* **❌ 致命违规**：将读取到的数据赋值给当前 Feature 的私有全局字段（如 `this._cachedPrices = ctx.UsePort(...)`）。在下一帧，这些内存可能已经被覆盖，会导致幽灵残影和并发异常。
* **✅ 唯一正道**：用完即走。每帧 `Project` 必须重新调用 `UsePort` 拉取最新切片。

## 2. 渲染期“单向数据流” (Read-Only Project Phase)
* **物理机制**：`Project` / `OnProject` 阶段处于渲染管线最末端，此时依赖有向无环图 (DAG) 已经锁定。
* **❌ 致命违规**：在 `Project` 函数内部调用 `board.Write(...)` 或 `ctx.Shared().Publish(...)`。这属于“边画图边修改图纸”，极易引发无限重绘死循环（DFS 查环报错）。
* **✅ 唯一正道**：`Project` 阶段对黑板拥有**绝对的只读权**。状态派发（Write）必须在数据管线算子 (DataPipe) 或前端交互事件 (OnMouse) 中完成。

## 3. 强制“防空/越界”核验 (Mandatory Validation)
* **物理机制**：为追求 0-GC，无数据时引脚往往传递 `RealRange.Empty` 或 `Span.Empty`，而非 `null`。
* **❌ 致命违规**：拿到数据后直接调用 `.Span[0]` 或代入跨度计算 `span = max - min`。当用户缩放到极限或暂无数据时，直接击穿 UI 线程引发崩溃。
* **✅ 唯一正道**：在 `UsePort` 解包之后，必须写入 `if (!range.IsValid)` 或 `data.Length == 0` 的防空短路拦截（Short-circuit return）。

## 4. 绝对遵守“Hooks 铁律” (No Conditional UsePort)
* **物理机制**：底层的 `UsePort` 和 `UseDynamicMemo` 依赖状态机或 Hash 键进行依赖追踪。
* **❌ 致命违规**：将 `ctx.UsePort()` 写在 `if (!range.IsValid) return;` 之后，或者将其放在特定的逻辑分支内部。这会导致图表切入无效帧时，游标或状态错位，引发 `HEVO003` 崩溃。
* **✅ 唯一正道**：所有的 `UsePort` **必须**在 `Project` 函数的**最顶层、无条件、按严格固定顺序**全部执行完毕！所有的业务防空短路必须放在解包之后进行。

## 构建与交互的协议 (The Assembly & Interaction Protocol)

### 1. 业务图表组装与领域构建协议 (The Scoped Builder Protocol)

在重写 `ReactiveSchema.DefineFeatures` 时，**严禁**直接使用 `context.Add()` 散装调用。必须通过四大数学与物理领域构建器进行结构化组装，以保证物理拓扑的正确性：

* **🌍 `Environment` (物理环境)**：处理布局 (`SetupLayout`)、视口 (`SetupViewport`)、极值计算 (`SetupAutoScale`)、UI 装饰 (`Decor`)。
* **📏 `Axes` (坐标拓扑)**：处理自变量轴 (`AddDomainAxis`) 与因变量轴 (`AddRangeAxis`) 的数学映射。
* **🕯️ `Series` (视觉渲染)**：处理 K线、折线、Bar 图等实际渲染特征。
* **🖱️ `Interactions` (行为交互)**：处理十字光标、悬浮框、拖拽平移等逻辑。

#### 🚀 标准装配范例 (Standard Schema Assembly)

```csharp
protected override void DefineFeatures(IFeatureContext context)
{
    // 1. 注入全局特质 (SSOT)
    context.InjectTrait(ScaleStrategyTrait.Default);
    var xAxisMeta = FieldMeta.Literal("时间", new HevoSolidBrush(Colors.White), "HH:mm");

    // 2. 🌍 环境与布局
    context.Environment(env =>
    {
        env.SetupLayout(left: ChartLength.Pixel(100), bottom: ChartLength.Pixel(24))
           .SetupViewport(VP, minVisibleCount: 10, alignment: ViewportAlignment.LeftEdge)
           .SetupAutoScale(VP, YAxisRangePort, new[] { PricePort }, paddingRatio: 0.05);
           
        // 特殊：挂载业务头部装饰器 (劫持 VisualTree)
        env.SetupFinanceHeader((field, intervals) => { /* 业务逻辑 */ });
    })
    // 3. 📏 坐标系统映射
    .Axes(axes =>
    {
        axes.AddDomainAxis(TimePort, VP, xAxisMeta)
            .AddRangeAxis(YAxisRangePort, priceMeta, AxisPlacement.Right);
    })
    // 4. 🕯️ 数据序列渲染
    .Series(series =>
    {
        series.AddCandle(VP, YAxisRangePort, CandlePorts)
              .AddLine(YoYPort, YAxisRangePort, yoyMeta);
    })
    // 5. 🖱️ 交互行为
    .Interactions(interactions =>
    {
        // 💥 铁律：必须使用配置闭包，保持高内聚
        interactions.EnableStandardPointer(VP, HitPort, ChartInteractionMode.All)
                    .AddCrosshair(HitPort, TimePort, xAxisMeta, FormatFutureTimeLabel)
                    .AddTooltip(HitPort, TimePort, xAxisMeta);
    });
}
```

### 2. 运行时热插拔与 UI 事务 (UI Transaction)

在盘中动态切换指标（如勾选 MACD、移除 KDJ）时，**必须**使用 `Transact` 开启事务舱。

* **物理机制**：引擎在闭包结束后执行“智能 Diff”算法。被移除的特征会触发 `Decompose` 并**精准掐断其后台 Rx 订阅字典 (`_dynamicSubs`)**；新加入的特征通过 `WorkflowTrigger` 瞬间完成“初始数据脉冲”，实现无缝输血。
* **防御逻辑**：在事务外部调用 `Add/Remove` 会导致 UI 频繁重绘引发“画面撕裂”，框架会自动将其包装为隐式微型事务，但推荐显式调用以获得最高性能。
* **重入锁保护**：`Transact` 内部支持嵌套调用，由 `_isTransacting` 重入锁保证原子性。

#### 🚀 标准热插拔范例 (Hot-Plug Example)

```csharp
public void OnMacdVisibilityChanged(bool isVisible)
{
    // 💥 开启图表事务舱，内部执行 0-GC 智能 Diff
    this.Transact(context => 
    {
        if (isVisible)
        {
            // 原子挂载：瞬间触发底层 Workflow 脉冲输血
            context.Axes(a => a.AddRangeAxis(MACDRangePort, macdMeta))
                   .Series(s => s.AddMACD(VP, MACDRangePort, macdPorts));
        }
        else
        {
            // 原子移除：支持泛型条件精准狙击，自动清理后台订阅，防止内存泄漏
            context.Remove<MacdSeriesFeature>()
                   .Axes(a => a.Remove<AxisFeature>(ax => ax.Id.Contains("MACD")));
        }
    });
}
```

### 3. Feature 专属扩展方法设计 (High Cohesion Extensions)

为了维护代码的极端整洁，所有的“语法糖”（扩展方法）**严禁**堆砌在单一的 `Extensions` 大杂烩类中。必须遵循**“谁的孩子谁抱走”**原则，定义在各自 Feature 类所在的文件中。

* **分类归属**：扩展方法必须挂载到对应的领域构建器（`Environment` / `Axes` / `Series` / `Interactions`）上。
* **防重/防白屏机制**：对于具有物理排他性的特征（如 `SetupLayout`），扩展方法内部应先执行 `.Remove<T>()`，防止由于 `CompositeAspect` 的洋葱模型导致布局嵌套挤压（如双重 Grid 导致画布尺寸为 0）。

#### 🚀 扩展方法标准范式 (以 BarSeries 为例)

```csharp
namespace Hevo.Charting.Features
{
    public static class BarSeriesFeatureExtensions
    {
        /// <summary>
        /// 🕯️ 挂载柱状图序列
        /// </summary>
        // Viewport 由 ChartFeature.InternalCompose 从 ViewportManagerFeature.Ports 自动注入（L6 / §B.2.6）——业务层不再显式传 vp。
        // Axis 族（AddDomainAxis / AddRangeAxis）作为"端口绑定者"仍保留显式 port 参数。
        public static SeriesBuilder AddBar(this SeriesBuilder builder, DataPort<ReadOnlyMemory<double>> dataPort, DataPort<RealRange> rangePort, FieldMeta meta, double widthRatio = 0.8)
        {
            // 封装组件实例化细节，保持 Schema 纯粹声明式
            builder.Context.Add(new BarSeriesFeature
            {
                DataPort = dataPort,
                YRangePort = rangePort,
                Meta = meta,
                BarWidthRatio = widthRatio
            });
            return builder;
        }
    }
}
```

### 4. DataBlackboard 物理读取铁律 (0-GC Lifecycle)

在 V3.0 的响应式架构中，`OnProject` 是最高频执行的帧函数（每秒执行 60-120 次）。为了保证内存零抖动和时空一致性，必须严格遵守以下物理限制：

1.  **绝对禁止“跨帧缓存” (No Lifecycle Escape)**：
    * **物理特征**：通过 `ctx.UsePort()` 提取的 `ReadOnlyMemory<T>` 或 `Span<T>`，其底层内存寿命**仅限当前函数执行期**。
    * **❌ 致命违规**：将读取到的数据赋值给 Feature 的私有全局字段（如 `this._cachedPrices = ...`）。
    * **💥 后果**：下一帧内存可能被底层对象池回收或覆盖，导致屏幕出现**幽灵残影**、画面撕裂或严重的并发内存异常。

2.  **渲染期“绝对只读” (Write-Through Forbidden)**：
    * **物理特征**：`OnProject` 阶段处于渲染管线的最末端。
    * **❌ 致命违规**：在 `OnProject` 内部调用 `board.Write()` 或 `ctx.Shared().Publish()`。
    * **💥 后果**：这属于“边画图边改图纸”，会引发**递归死循环 (DFS Cyclic Error)**。状态变更必须在数据管线算子 (DataPipe) 或交互事件 (OnMouse) 中完成。

3.  **强制“防空短路” (Mandatory Validation)**：
    * **物理特征**：在数据拉取的真空期（如网络加载中），引脚数据可能为空。
    * **✅ 唯一正道**：解包引脚后，必须紧跟 `if (!range.IsValid)` 或 `data.IsEmpty` 拦截逻辑。
    * **💥 铁律**：严禁在未检查长度的情况下进行 `data.Span[0]` 计算，防止击穿 UI 线程引发崩溃。

4.  **Hooks 铁律 (Unconditional Execution)**：
    * **物理特征**：底层的 `UsePort` 和 `UseDynamicMemo` 依赖内部游标和状态机进行依赖追踪。
    * **❌ 致命违规**：将其放入 `if/else` 分支内部，或放在任何可能被 `return` 提前截断的逻辑之后。
    * **💥 后果**：这会导致图表切入无效帧时游标错位，引发 `HEVO003` 架构崩溃报错。**所有 UsePort 调用必须在函数最顶层、无条件、按严格固定顺序排列！**

### 5. 交互协议与逆向碰撞 (Interaction & Scale Invert)

交互（如十字光标、吸附、碰撞检测）本质上是一个回环数据流。**架构红线：严禁在业务层手写物理坐标映射公式。**

1. **Event Source**：在 `ChartFeature` 中使用 `WithBoard(this.OnMouse(...)).Subscribe(...)` 获取高频输入；若需要读/写黑板，必须在回调内部显式获取 `AcquireReadLock()` / `AcquireUpgradeableReadLock()` / `AcquireWriteLock()`。
2.  **逆向碰撞 (Scale Invert)**：读取 `ScaleStrategyTrait`，调用 `DomainScale.Denormalize(p.X, area)` 将像素坐标转换为逻辑索引（Logical Index）。
3.  **黑板播报 (Broadcast)**：将计算出的逻辑索引封装为 `0-GC PointerHitState` 结构体，通过 `board.WriteIfChanged` 写入黑板总线。
4.  **终端渲染 (Rendering)**：具体的图层（如 `CrosshairLayer`）监听该引脚，利用逻辑索引重新进行“居中吸附”的正向投影，确保视觉上永远精准对齐 K 线中心。

### 6. 组件配置单点事实源 (FieldMeta SSOT)

为了保持框架 API 的高度内聚，严禁在交互组件中散落定义 `XLabelFormat`, `TooltipColor` 等零散属性。

* **SSOT 准则**：必须使用框架标准的 `FieldMeta` 记录类 (record class)，统一管理组件的“名称、格式、画笔颜色、Provider”。
* **联动效应**：在 Schema 组装期实例化一次 `FieldMeta`，并显式分发给轴（Axis）、光标（Crosshair）和提示框（Tooltip），实现一处重构，全场联动。

```csharp
// 1. 在 Schema 中定义唯一事实源
var xAxisMeta = FieldMeta.Literal("时间", new HevoSolidBrush(Colors.White), "MM-dd HH:mm");

// 2. 强绑定分发，保证交互时的格式与轴标签 100% 对齐
context.Axes(a => a.AddDomainAxis(TimePort, VP, xAxisMeta))
       .Interactions(i => i.AddCrosshair(HitPort, TimePort, xAxisMeta));
```

### 7. 性能保护：智能脏检查 (Smart Dirty-Check)

框架通过 `StateClock`（环境纪元）和 `DataPort.Tick`（引脚时钟）实现三级增量渲染拦截，确保 CPU 每一毫秒的计算都物超所值：

* **重型渲染兵 (Series Features)**：
    * **机制**：必须通过 `[Port]` 标签标记引脚属性。
    * **智能拦截**：框架在每帧开始前会自动比对引脚的 `CurrentTick`。若所有引脚数据未变，且全局环境版本（`VersionToken`）一致，引擎将**直接跳过 `OnProject` 的执行**。
    * **✅ 结果**：在行情静止或用户未操作时，图表执行开销降为 **O(1)**。

* **轻型交互兵 (Interaction Features)**：
    * **机制**：严禁无条件重绘，必须采用响应式流。
    * **精准唤醒**：通过 `flow.Watch(HitPort)` 或 `this.OnMouse()` 挂载监听。只有当特定的物理引脚（如鼠标坐标、逻辑索引）发生位移时，逻辑才会被唤醒。
    * **✅ 结果**：彻底告别“每帧盲目计算”，将交互开销控制在**按需触发**。

* **环境纪元同步 (Environment Clock)**：
    * **触发场景**：窗口尺寸改变（Resizing）、皮肤切换（Theme Change）或事务提交（`Transact`）。
    * **强制刷新**：`_environmentClock.Advance()` 会产生全新的 `VersionToken`。此时，即便引脚数据未变，框架也会强制所有特征执行一次“环境对齐”，以确保物理地基的绝对同步。

得益于 `DataPort` 的绝对解耦，我们的 Feature 变成了纯函数节点。无需启动 UI 线程，即可毫秒级完成复杂图表逻辑验证：

## 抽象基类迁移模式 (Schema Inheritance Pattern)

当同一业务域存在 **3 个以上模板相同、仅参数不同的 Schema** 时，应将共用的 `DefineDataFlow` / `DefineFeatures` 逻辑沉入抽象基类，子类只声明差异化属性。

### 示例：DualTimeShareSchemaBase

```csharp
// 基类：在 Hevo.Drawing/TimeShare/DualTimeShareSchemaBase.cs
public abstract class DualTimeShareSchemaBase : ReactiveSchema
{
    protected abstract Security MainSecurity { get; }
    protected abstract string MainTitle { get; }
    protected virtual Security BaselineSecurity => new("USHI", new Code("1A0001"));
    protected virtual string BaselineTitle => "上证指数";

    // DefineDataFlow / DefineFeatures 全部在基类实现
}

// 子类：5 行即完成一个独立业务图表
public class YesterdayHighAmpSchema : DualTimeShareSchemaBase
{
    protected override Security MainSecurity => new("URFI", new Code("883906"));
    protected override string MainTitle => "昨日高振幅";
}
```

### 适用判断准则

| 条件 | 做法 |
| ---- | ---- |
| ≥3 个 Schema 模板一致，仅证券代码/标题不同 | **继承** `DualTimeShareSchemaBase` 或同类基类 |
| 源数目或 Feature 结构存在差异 | **直接使用** `TimeAxisCoordinator` 手动装配 |
| 动态源（运行期加减） | 使用 `DynamicSchema` + `TimeAxisCoordinator`；资源通过 `this.Own(...)` 托管 |

## 附录：开发者快速自检 Checklist

在提交任何 Schema 或 Feature 代码前，请逐一核对以下**“避坑指南”**：

### 1. 物理防崩 (Stability)
- [ ] **引脚合规**：所有通过反射注入的 `DataPort<T>` 属性是否标记了 `null!`？
- [ ] **消灭压制**：代码中是否已彻底移除一切非法的 `!` (感叹号) 后缀？(严禁欺骗编译器，必须通过 `if` 或 `??` 解决 null)。
- [ ] **白屏防御**：`Environment` 域是否显式配置了 `SetupLayout`？(未配置将导致默认 Margin 嵌套挤压，画布尺寸缩减为 0)。

### 2. 内存与并发安全 (Memory & Concurrency)
- [ ] **事务包裹**：盘中所有动态增删指标的操作，是否全部包裹在 `this.Transact(context => { ... })` 中？
- [ ] **订阅托管**：所有的 `Workflow.Subscribe` 返回值是否全部存入了 `_dynamicSubs` 字典（针对动态 Feature）或托管给了 `ChartSession`？
- [ ] **0-GC 铁律**：`OnProject` 内部是否存在任何 `new` 对象、`LINQ` 调用或未标记为 `static` 的 Lambda 闭包？

### 3. 架构纯净度 (Architectural Purity)
- [ ] **高内聚扩展**：你的 `AddXXX` 语法糖是否写在对应 Feature 类所在的文件中？(严禁堆砌在大杂烩 Extensions 类里)。
- [ ] **数学解耦**：Layer 内部绘制时是否通过 `ScaleStrategyTrait` 进行投影？**绝对严禁**手写 `(x - min) / span * width` 这种硬编码数学公式。
- [ ] **SSOT 对齐**：颜色、格式化字符串等属性是否统一通过 `FieldMeta` 记录类进行分发和注入？
